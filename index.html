Foundations of the system

Overview

Design principles, product intent, and the rules that govern every decision made with this system. Read this section in full before contributing a pattern.

Principles
00.1

What this system is for

The Enterprise Automation Interface System governs software used by operators who run unattended processes across thousands of machines. These users are not browsing — they are monitoring, diagnosing and remediating. Sessions last for hours, screens are dense, and every pixel competes for attention.

That context dictates the entire visual strategy. The interface is dark by default because these tools are used in dim NOC environments and alongside terminal sessions; rows are 36 px because operators need breadth of context on one screen; and colour is rationed because in an alerting surface, colour is a signal, not decoration.

The governing heuristic: an operator should be able to scan a screen of live automation state and identify what needs their attention in under three seconds — without reading a single word.
00.2

Product principles

1

Progressive disclosure over completeness

Show the decision-critical surface first. Expensive detail — raw payloads, full stack traces, verbose history — lives behind an explicit interaction. Never hide state behind hover alone.

2

Status is the primary content

Status colour, iconography and text are a single unified tri-channel signal. Colour alone is never sufficient — WCAG 1.4.1 requires a redundant non-colour cue.

3

Destructive actions are reversible or fenced

Anything that halts, deletes or force-stops a process requires a confirmation step naming the exact target and its blast radius. Cancel is always adjacent.

4

Tighter rows fit more state

Target 13.5–15px body text on an 8px internal rhythm. Prefer tighter rows and tabular numerics over generous whitespace; operators optimise for information per screen, not for air.

5

Keyboard is the primary input

Every workflow must be completable without a pointer. Logical tab order, visible focus rings, and documented shortcuts are requirements — not enhancements.

6

The system is closed

No raw hex values, arbitrary pixel values, or one-off radii in product code. If the system lacks a token, that is a proposal to the system, not a local decision.

00.3

Usage rules

Binding constraints for anyone producing interface work.

These rules are not stylistic preferences. Violating them makes the product measurably harder to operate, harder to hand over between teams, and harder to maintain across releases.

  1. Consume semantic tokens only. Product code references --surface-raised, never --gray-850. Primitives may change without notice; semantics will not.
  2. Never hard-code spacing. All gaps, paddings and insets come from the 4px scale. An arbitrary 13px margin is a defect, not a decision.
  3. One primary action per view. A screen may present at most one filled primary button in its visual field of view. Everything else is secondary, ghost, or tertiary.
  4. Reserve the accent. Brand blue means interactive or selected. It does not mean emphasis, category, or decoration. A blue heading implies the heading is clickable.
  5. Text is the accessible default. Icons augment labels, they do not replace them. If removing the text breaks the interface, the icon needs a aria-label and a tooltip.
  6. Layout must survive 200% zoom. No fixed-height text containers, no text baked into images, no horizontal scroll at 320px CSS width.
  7. Motion explains, never performs. Animation duration stays under 300ms and must be suppressible via prefers-reduced-motion.
Contribution workflow. New or changed patterns require: a Figma component with variants, a documented anatomy, all interactive states, an accessibility note, and engineering sign-off. Anything shipping without a token reference will be rejected at code review.

✓

Use semantic tokens in product code

Write var(--bg-surface-2). A primitive reference in application code will break silently at the next palette re-grade.

✕

Don't introduce off-system hues

If a new colour is genuinely required (e.g. a vendor brand mark), it must be added as a primitive scale with documented purpose, then bound to a semantic role.

✓

Limit a view to three status colours

More than three competing status hues in one viewport destroys the pre-attentive benefit of colour and increases misreads under fatigue.

✕

Don't encode meaning in hue alone

Every status must pair colour with an icon, a label, or both. Roughly 1 in 12 men has a red-green deficiency; operators are not exempt.

✓

Reserve pure white for maximum emphasis

--text-primary is near-white (#F6F8FA). Reserve #FFFFFF for the highest-emphasis value in a view only.

✕

Don't use brand blue as decoration

Accent blue signals interactivity or selection. Using it for a heading, an icon, or a border to "add some colour" actively misleads the operator.

02.4

Paragraph measure

Line length is capped per style to preserve readability.

Too narrow — causes ragged line breaks, forces the eye to jump back every two or three words, and measurably slows comprehension even in a technical audience reading short bursts of operational copy over long shifts.
22ch — over-constrained
Ideal measure sits between 60 and 78 characters. Use the full container width for tables and lists, but cap continuous prose at 78 characters and align it to the left — never centred — because centred text has no consistent left edge for the eye to return to.
68ch — correct
Too wide — the return sweep becomes unreliable, readers lose their place, and each new line requires a corrective eye movement that is measurable as additional time and reduced comprehension. This is the most common failure in review and audit screens, where dense tables and long descriptive cells get combined without any measure control at all.

02.6

Writing rules

Interface copy is a functional component. These rules govern every string in the product.

Voice & tone

We are precise, calm, and never cute. This is infrastructure software used by people who are often under pressure. The writing should feel like a competent colleague handing you the facts.

  • Neutral and factual. Describe the state, not your feelings about it.
  • Direct. Lead with the verb or the noun. No throat-clearing.
  • Confident. "Deployment failed." not "It seems the deployment may have failed."
  • Human. "Save changes" not "Submit". Contractions are fine in guidance copy.
  • No humour in failure paths. An operator seeing "Deployment failed" at 03:00 should not be reading a joke.

Mechanics

Case
Sentence case for everything except overline labels
Buttons
Verb first, 1–3 words — "Create job"
Headings
No trailing punctuation, no colons
Lists
Parallel grammatical structure, Oxford comma
Numbers
Locale-aware separators; tabular figures in columns
Time
Relative for recency ("4m ago"), absolute for audit
Ellipsis
Use the … character, never three periods
Quotes
Curly quotes “ ” in prose, straight in code
Acronyms
Expand on first use per view

Error message formula

[what] +
[what went wrong] +
[what to do next]

Bad

"Error 500. Internal Server Error."

Good

"Couldn't save the schedule. The name is already in use on this project. Try a different name."

✓

Start buttons with a verb

"Save changes", "Run now", "Delete pipeline". Never "Submit", "OK", or "Yes".

✕

Don't blame the user

"You entered an invalid value" → "That value must be between 1 and 9999".

✓

Say what will happen

Destructive buttons read "Delete 3 pipelines", not just "Delete".

✕

Don't use ALL CAPS for emphasis

It destroys scannability and reads as shouting. Use weight, size or colour instead.

✓

Keep strings localisable

No string concatenation for sentences, no pluralisation baked in — use ICU message format.

✕

Don't use placeholder text as a label

Labels must persist. Placeholders disappear exactly when the operator needs to check the expected format.

Radius rules

04.4

Usage rules

Consolidated do / don't list for all components. Each rule links to a documented failure mode.

Do

Recommended patterns

✓

One primary action per view

All other actions step down to secondary, ghost, or text-link. The eye should know where to go without deliberation.

✓

Place the primary action last in DOM order

A screen reads left-to-right; the terminal action belongs at the end of the flow, and usually at the end of the row.

✓

Use icons alongside labels for high-risk actions

Delete, force-stop and revoke warrant an explicit verb. The icon reinforces; it never replaces the word.

✓

Group related fields in a fieldset

Related inputs share a legend; optional advanced settings sit behind a disclosure so forms stay compact by default.

✓

Keep status badges adjacent to their subject

A badge in a table cell belongs on the same row as the resource it describes — never in a separate status column far right.

✓

Reserve modals for decisions that must be made now

A modal that can be deferred should be a drawer. A modal that only displays information should be an inline panel.

Don't

Anti-patterns

✕

Don't use two primary buttons side by side

Competing primaries force a decision the operator hasn't been given context to make. Choose a default and demote the alternative.

✕

Don't use colour as the only state signal

Required for accessibility and for the ~8% of operators with a colour vision deficiency reading a wall of status.

✕

Don't disable a submit button without explanation

An inert button is a dead end. Show the form validation errors, or surface a tooltip explaining what is missing.

✕

Don't hide destructive actions in overflow menus

A one-click path to irreversible damage must be discoverable and labelled. Hide frequency, not risk.

✕

Don't mix radius or spacing families

One radius family and one spacing rhythm per surface. Hybrid styling reads as "not finished".

✕

Don't rely on hover for discoverable information

No essential content may exist only on pointer hover. Tooltips are supplementary, never load-bearing.

Button rules

✓

Verb-first labels

"Create job", "Run now", "Save draft". One to three words, sentence case.

✕

Don't use "OK" or "Submit"

"OK" forces the operator to read the surrounding copy to work out what happens next.

✓

Pair destructive buttons with a modal

The button initiates; the dialog commits. Name the target and the count in the confirmation.

✕

Don't use ghost for the primary action

A ghost primary has insufficient visual weight to anchor a layout in a dense, dark interface.

✓

Keep icon size consistent within a row

Mixing 13px and 15px icons across adjacent buttons reads as a rendering bug.

Field rules

✓

Always show a visible label

Placeholders vanish on focus and on input. A label is required on every field, no exceptions.

✕

Don't rely on the placeholder as an example

If the expected format matters, put a real example in the helper text, below the control.

✓

Mark required fields explicitly

A trailing asterisk plus aria-required. Don't mark optional fields instead — the majority are required.

✕

Don't validate on every keystroke

Validate on blur. Re-validate live only after the field has already errored once.

✓

Link the message with aria-describedby

The error text must be programmatically associated with the input, not just placed beneath it.

✕

Don't use colour alone for errors

Red border plus an icon plus text. The icon is what makes it readable to everyone.

Badge rules

✓

Pair every colour with a dot and a word

The dot is the redundant cue for colour vision deficiency. Never ship a bare coloured pill.

✕

Don't use badges for counts of arbitrary things

A neutral count pill is fine; a coloured one implies a status the number doesn't carry.

✓

Keep labels to one or two words

A badge is a glance target, not a sentence. "Degraded" not "Performance degraded".

✕

Don't animate badges into place

No slide, bounce, or scale. A status change cross-fades in 260ms and nothing else.

✓

Limit solid badges to one per view

Solid fills are the loudest element in the badge family. Two of them means neither is an alarm.

Nav rules

✓

Exactly one active item per group

If two items are highlighted the operator cannot tell where they are.

✕

Don't move the active rail on hover

The 3px indicator marks position, not interaction. It stays put until the route changes.

✓

Group items under a labelled heading

Over 7 top-level items, group them. Over 15, move them into a searchable command palette.

✕

Don't put nav items in a scroll-jacked menu

The rail is always fully visible. Collapsing to icons is allowed; hiding is not.

✓

Show a count on items that need attention

Use neutral for informational counts, danger styling only for genuine action required.

Handoff & implementation

Token references, naming conventions, and the code contract that keeps design and engineering in sync.

Token delivery

How primitives and semantics reach the product runtime.

/* Layer 1 — primitives (raw values) */
:root {
  --gray-900: #121922;
  --blue-500: #1F6FEB;
  --green-500: #12A970;
}

/* Layer 2 — semantics (product contract) */
:root {
  --bg-surface:      var(--gray-900);
  --text-primary:    var(--gray-50);
  --accent:          var(--blue-500);
  --success:         var(--green-500);
}

/* Themed override — future light theme */
[data-theme="light"] {
  --bg-surface:   #FFFFFF;
  --text-primary: #0B1118;
}
Because semantics are the only layer product code touches, a light theme is a single [data-theme] attribute change — no component edits, no rebuild of the semantic map.
